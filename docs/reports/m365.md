# M365 Assessment Report

The M365 report (`lib/reports/m365.py`, `scripts/generate_m365_report.py`) is a dedicated 9-tab Excel
workbook for Microsoft 365 (Exchange, SharePoint, OneDrive, Teams), built specifically to feed the Cohesity
Web Sizing Tool (WST). It does not merge with AWS/Azure/GCP inventory. For multi-cloud infrastructure, use
the [Assessment Report](assessment.md) instead.

## Basic Usage

```bash
# Auto-discover M365 inventory files in a directory (recursive, and content-checked - see below)
python scripts/generate_m365_report.py --directory ./cca_output

# Specify files directly
python scripts/generate_m365_report.py --inventory cca_m365_inv_*.json

# Filter to a specific set of users (e.g. only users actually in scope for backup)
python scripts/generate_m365_report.py --filter-users backup_users.csv -o filtered_report.xlsx
```

`find_m365_files()`'s auto-discovery is stricter than the other reports': it doesn't just glob a filename
pattern, it opens every matching file and checks `provider == 'microsoft365'` (on the first array element, if
the file is a bare list, or on the top-level dict) before including it. A `cca_inv_*.json` from a different
collector sitting in the same directory won't be pulled in by mistake.

## Inputs: the Summary File Pairing Is Load-Bearing

Most of this report's real value (mailbox-type breakdowns, DCR/AGR change rates, per-user license
assignments, tenant/licensing info) comes from a **separate summary file**, not the inventory file itself.
`load_summary_data()` finds it with a **naive string substitution**: for each inventory path, it replaces
the substring `_inv_` with `_sum_` and tries to load whatever that produces. If the summary file isn't
sitting right next to the inventory file with that exact naming convention (same directory, same timestamp,
just `_inv_` → `_sum_`), `load_json_file()` fails silently (caught `FileNotFoundError`, loop just
`continue`s) and every tab that depends on it quietly falls back to a cruder calculation from raw resources
instead of erroring. You won't get a warning that you're looking at the degraded version. Concretely, this
affects:

- Executive Summary's licensing section (missing entirely without a summary file)
- Sizing Inputs' per-mailbox-type WST breakdown (falls back to one flat Exchange/SharePoint/OneDrive total each, losing the User/Archive/SoftDeleted/Group/PublicFolder split the WST sizer actually wants)
- The entire License Assignments tab (`user_license_assignments` requires `User.Read.All` Graph permission *and* the summary file; without either, the tab just says so and stops)
- Growth Analysis (falls back to three hardcoded "industry typical" percentage estimates, not your tenant's actual data)

## How Each Tab's Values Are Determined

### 1. Executive Summary

- **Total Users**: `summary_data['total_user_count']`, from the summary file. If the M365 collector hit Graph API's pagination cap while enumerating users, the label itself changes to append "(pagination cap hit - likely undercounted)" - a real, not cosmetic, data-completeness warning worth reading literally.
- **Licensing section**: filters the tenant's full SKU list down to M365-relevant ones via a hardcoded include/exclude substring match on SKU name (`is_m365_sku()`) - includes anything matching `SPE_`, `M365_`, `ENTERPRISE`, `EXCHANGE`, `TEAMS`, `DEFENDER`, etc.; excludes anything matching `_FREE`, `_TRIAL`, `STREAM`, etc. This is a maintained allowlist/denylist of known SKU name substrings, not a Graph API field that marks a SKU as "M365"; a newly-introduced SKU name that doesn't match either list won't appear in this section at all.
- **Storage Summary by Service**: Teams storage is **not** read from a Teams API field. It's attributed from SharePoint sites whose `metadata.root_web_template` is `Group` or `Team Channel` (Teams' file storage lives in SharePoint under the hood), pulled out of the SharePoint bucket and into the Teams bucket. If no resources carry that metadata but `change_rates['SharePoint']` exists, SharePoint's size is *itself* reverse-estimated as `daily_change_gb / (daily_change_percent / 100)` and flagged `(estimated)` in the sheet. This means the Executive Summary's SharePoint total and the SharePoint Online tab's total are **not the same calculation** - the SharePoint tab (see below) counts Group/Team Channel sites as SharePoint, while Executive Summary moves them into Teams.
- **Quick Statistics**: archive-enabled/soft-deleted mailbox counts and deleted-site counts come from the summary file's `exchange_mailbox_breakdown`/`sharepoint_site_breakdown`, not recomputed from the resource list shown on the Exchange/SharePoint tabs.

### 2. Exchange Online

Mailbox type, archive/deleted status, and quota-utilization buckets are all read directly from each
`m365:mailbox`-type resource's own `metadata` fields (`mailbox_type`, `has_archive`, `is_deleted`,
`quota_usage_percent`); none of this is inferred or estimated. "Top 10 Largest Mailboxes" is a straight sort
by `size_gb` descending, capped at 10 rows (not configurable, not noted when truncated beyond 10, unlike the
assessment report's 500-row cap note on Unprotected Resources).

### 3. SharePoint Online

Site type distribution uses `metadata.root_web_template` (falling back to `metadata.site_type`) with no
Teams-site exclusion: `Group` and `Team Channel` sites are counted here as SharePoint, same as every other
site type. This is the deliberate inconsistency noted above versus Executive Summary, which pulls those same
sites out into the Teams bucket. If you're reconciling "why doesn't SharePoint's total here match the
Executive Summary" for a customer, this is the answer.

### 4. OneDrive for Business

Direct per-account listing, sorted by size descending. No estimation or fallback logic.

### 5. Microsoft Teams

Team count and archived/active split come directly from `m365:teams`-type resources' own
`metadata.is_archived` flag. Activity metrics (active users, message counts) come from the summary file's
`teams_activity` block, not from the Teams resources themselves.

### 6. Sizing Inputs (feeds the Cohesity WST)

The tab most worth reading closely before handing a number to a customer, since every value here is meant
to be typed directly into Cohesity's sizing calculator:

- **Exchange/SharePoint/OneDrive rows**: when the summary file's `exchange_summary`/`sharepoint_summary`/`onedrive_summary` blocks are present, this tab reproduces the WST's own category breakdown exactly (User Active / Archive-enabled / SoftDeleted Active / SoftDeleted Archive / Group / Public Folder mailboxes, each with its own count and size). **Archive and SoftDeleted-Archive mailbox sizes are never populated** - only counts - because getting their actual size requires an Exchange PowerShell session the Graph-API-based collector doesn't have; this is called out in both the row label and the Notes section, not silently left blank.
- **DCR (Daily Change Rate) / AGR (Annual Growth Rate)**: pulled directly from the summary file's `change_rates` block when present (Microsoft's own storage usage history, sampled by the collector). When absent, these columns are simply blank for that workload, not estimated with a placeholder - contrast with Growth Analysis (below), which *does* substitute hardcoded industry estimates when `change_rates` is entirely missing.
- **SharePoint fallback when no summary file exists**: same reverse-estimation as Executive Summary (`daily_change_gb / (daily_change_percent / 100)`), labeled "(est. from change rate)" in the workload-type cell.
- **Teams Chat metered units**: `estimated_metered_units_user_chats`/`_channel_conversations` from the summary file, falling back to raw `private_chat_messages`/`team_chat_messages` counts if the pre-computed metered-unit fields aren't present. "WST Input" projects this to an annual figure with `total_metered * 12` as its fallback (only used when the collector hasn't already supplied `projected_annual_metered_units` directly) - note that `total_metered` is explicitly a **180-day** total, so multiplying it by 12 treats it as if it were a monthly figure being annualized rather than a 180-day one. Confirm this matches what the WST actually expects before typing the result in directly.
- **WST On-Prem Cluster Sizing Guidance**: `estimated_objects = licensed_users * 4` - a rough rule of thumb (roughly one object each for mailbox, OneDrive, SharePoint, and Teams per user), **not a real count** of actual mailboxes + sites + teams. Treat the resulting "Estimated clusters required" figure as a ballpark, not a sizing commitment; the real object counts are calculable from the resource list but this tab doesn't do that math anywhere.
- **Licensed Users (in scope)**: when `--filter-users` was used, this becomes the count of users actually found with resources (mailbox/OneDrive/EntraID user) in the filtered set, not the filter CSV's row count - a user listed in the CSV with no matching mailbox/OneDrive resource in the inventory won't be counted.

### 7. License Assignments

Entirely dependent on the summary file's `user_license_assignments` (requires `User.Read.All` during
collection; the tab says so and stops if it's missing). License Pool Summary utilization coloring: ≥90% red,
≥75% yellow, else green - a fixed threshold, not customer-configurable. "Users without Licenses" commonly
includes shared mailboxes, service accounts, and guests, not just unused seats; the Notes section says this
explicitly, worth repeating if you forward this sheet without the notes.

### 8. Growth Analysis

If the summary file's `change_rates` block is present, shows the measured daily-change-GB/percent and
annual-growth-percent per service, taken as-is from Microsoft's own usage history (same source as Sizing
Inputs' DCR/AGR columns). If absent, the tab falls back to three **hardcoded "industry typical" estimates**
(Exchange 2-3%, OneDrive 3-5%, SharePoint 2-4% daily) that have nothing to do with this specific tenant - read
the "Notes available" fallback for what it says if you're not sure which case you're in.

### 9. Raw Data

Every resource, name and resource ID truncated to 40 characters, dates truncated to `YYYY-MM-DD`. The
"Type/Status" column means something different per resource type (mailbox type for Exchange, site type for
SharePoint, Archived/Active for Teams) and is blank for everything else.

## The `--filter-users` Path Changes What Several Tabs Mean

When a filter CSV is supplied, `generate_report()` doesn't just drop out-of-scope resources; it also
**clears** `exchange_summary`/`sharepoint_summary`/`onedrive_summary`/`exchange_mailbox_breakdown` from the
summary data entirely (even if the summary file had them), so every tab that would otherwise use the
WST-aligned per-category breakdown falls back to the cruder "sum of filtered resources" calculation instead.
`total_user_count` is also replaced with a count of unique UPNs that actually have a matching
mailbox/OneDrive/EntraID-user resource in the filtered set, which can be lower than the filter CSV's row
count if some listed users have no matching resource.

## Known Limitations Checklist

- [ ] Is the summary file (`_sum_` to match the inventory file's `_inv_`) actually present next to the inventory file? If a tab looks suspiciously sparse, this is the first thing to check, and `load_summary_data()` will not tell you it's missing.
- [ ] Are you reconciling SharePoint totals between the Executive Summary and the SharePoint Online tab? They intentionally differ because Executive Summary excludes Group/Team Channel sites (attributed to Teams) and the SharePoint tab doesn't.
- [ ] Is "Total Users" flagged "(pagination cap hit - likely undercounted)"? Take that literally; it is not a cosmetic label.
- [ ] Are you about to quote "Estimated clusters required" or "estimated objects" from the WST Sizing Guidance section? That's `licensed_users × 4`, a rule of thumb, not a measured object count.
- [ ] Did you use `--filter-users`? If so, every per-category WST breakdown (Exchange/SharePoint/OneDrive summaries) has been dropped in favor of cruder totals, even if the summary file had the detailed version.
- [ ] Are the DCR/AGR or Growth Analysis numbers real measured values, or the hardcoded "industry typical" fallback? Check whether `change_rates` was present in the summary file; the fallback path produces plausible-looking percentages with no connection to this tenant.
